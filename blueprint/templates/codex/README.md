# Codex Integration Layer

OPTIONAL dual-runtime setup. `.codex/` is a **pointer layer** over `.claude/` — it holds routing and sandbox config, never protocol. Delete the whole directory and the pipeline runs unchanged on Claude Code alone.

Everything below is derived from a working installation probed against **codex 0.144.1**. Where the harness's documented behaviour and its measured behaviour disagree, this file records the measurement and says so. Re-probe on a codex upgrade.

---

## The one rule

**`.claude/` is the single source of truth. `.codex/` never restates it.**

Every file under `.codex/skills/` either symlinks a `.claude/` directory or is a generated pointer that says "read this `.claude/` file in full". The only hand-authored bytes in the whole layer are (a) `config.toml`, (b) `rules/*.rules`, (c) `agents/*.toml`, and (d) a small set of hand-written cards covering harness mechanics that `.claude/` has no reason to know about.

If you catch yourself writing what to build inside `.codex/`, it belongs in `.claude/`.

---

## Layout

```
.codex/
├── config.toml                 ← model + sandbox reach. NOT launch flags.
├── rules/
│   └── repo-law.rules          ← execpolicy door lock (filename arbitrary)
├── agents/                     ← role registry — INERT today, ships forward-compatible
│   ├── mono-documenter.toml    ← root role (one instance, no roster expansion)
│   └── per-project/
│       ├── developer.toml      ← PATTERN — SETUP expands once per roster entry
│       └── qa.toml             ← PATTERN — same shape, MODES in the description
└── skills/                     ← GENERATED by scripts/codex-mirror.sh + hand-written cards
    ├── {command-name}/SKILL.md ← generated pointer (one per single-file command)
    ├── {skill-name} -> ../../.claude/skills/{skill-name}     ← true dir symlink
    ├── chat/SKILL.md           ← hand-written card (never overwritten)
    └── wave-builder/SKILL.md   ← hand-written card (never overwritten)

AGENTS.md -> CLAUDE.md          ← at the repo root; Codex reads AGENTS.md
```

## Setup

**1. `AGENTS.md` symlink** — Codex reads `AGENTS.md` as its project doc:

```bash
ln -s CLAUDE.md AGENTS.md
```

One file, both runtimes, no drift. Do not copy it.

**2. Config** — `cp templates/codex/config.toml .codex/config.toml`, then fill the model and reasoning-effort values. Read its comments before adding anything else; § "Settings deliberately absent" below explains what was removed and why.

**3. Rules** — `cp templates/codex/rules/repo-law.rules .codex/rules/`, fill the tool names, then PROVE each rule fires:

```bash
codex execpolicy check --pretty --rules .codex/rules/repo-law.rules -- {command}
```

**4. Mirror the entry points** — this is the whole `skills/` layer:

```bash
.claude/scripts/codex-mirror.sh generate
```

**5. Agents** — copy the `agents/` patterns and expand `{project}` per roster entry. Read the INERT ruling below first so you know what you are and are not getting.

**6. Trust the repo** — Codex only loads a repo-level `config.toml` for a trusted project; it asks once, on first launch in the directory.

## The mirror generator (`scripts/codex-mirror.sh`)

`.codex/skills/` is **generated**. Never hand-edit a pointer, and never vendor a copy of a `.claude/` protocol into it — a vendored copy is stale the first time the source changes, and nothing tells you.

### Two shapes, and why the difference is not negotiable

| Claude entry point                    | Mirrored as                              | Why                                                          |
| ------------------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| a **skill** (already a directory)     | true symlink to that directory           | zero generated bytes; Codex follows a symlinked skill DIR     |
| a **command** (a single `.md` file)   | a real directory + generated `SKILL.md`  | it has no directory to link, and linking the FILE loses it    |

The second row is a **measured harness constraint**. Codex 0.144.1 follows a symlinked skill DIRECTORY, but silently DROPS a real directory whose `SKILL.md` is a symlinked FILE — no warning, no error, no log line; the skill simply does not exist. Measured on a 56-entry mirror: **9 skills discovered before the fix, 56 after**, with the same 56 directories on disk the whole time.

That failure mode is invisible, so a regression looks exactly like success. Re-probe before ever "simplifying" the pointers back into symlinks.

### Pointer paths are repo-relative — always

A generated pointer says `Read `.claude/commands/{x}.md` (relative to the repo root you were launched in)`. Repo-relative, never absolute, and this is load-bearing: worktrees materialize these committed files, so a lane must read **its own branch's** protocol. An absolute path would silently route every worktree lane to the main checkout's version — the lane would follow a protocol its branch does not contain, and every symptom would point somewhere else.

### Modes

```bash
.claude/scripts/codex-mirror.sh            # generate (default)
.claude/scripts/codex-mirror.sh check      # exit 1 on anything stale/missing
```

`check` is CI / pre-merge-gate material: a command whose frontmatter changed leaves Codex routing on a stale description until the mirror runs again. Both modes print a **coverage line** naming what was inspected and what was skipped — "nothing stale" is never allowed to read as "nothing here".

### Hand-written cards (`HANDWRITTEN`)

The `HANDWRITTEN` list at the top of the script names the `.codex/skills/` directories the generator must never touch. A card earns a place there only when it carries Codex-specific MECHANICS with no Claude-side equivalent — harness deltas, ping channel, launch command. Two ship as worked examples:

- **`wave-builder/`** — the lane dialect: `spawn_agent` dispatch, spool pings, inline GATE-1, the launch command. Read this one before writing your own.
- **`chat/`** — the ping toolset. Note it has no generated counterpart at all: `chat` is a HOST-level command family (`~/.claude/commands/chat/`, not this repo's `.claude/commands/`), so the mirror — which only scans `.claude/commands/**` — never sees it and generates nothing for it; this hand-written card is its only Codex-side entry point.

A hand-written card still points at the binding protocol first and only then lists deltas. A card that explains what to build is a bug.

## Dispatch — how Codex actually spawns work

Codex spawns children with `spawn_agent{task_name, message, fork_turns}`. What that gives you:

- **Anonymous forked children.** The child is a fork of your own turn context. There is **no agent-selection parameter** — nothing in the call can name a role, a file, or a registry entry.
- **The message is the only binding.** The role comes from the protocol pointer you put in the message text, and nowhere else.

So the working dispatch shape is one child per role, with the pointer bound in the message:

```
You are the {role} role: read {project}/.claude/agents/{role}.md in full and execute it
exactly. {span work-list}. Stamp every deliverable: Executor: codex-subagent/{role}_{project}
```

Children share your cwd and sandbox, so every ban binds them identically. **Inline execution stays fully valid** — read the role manual, run it as part of your own span, stamp `Executor: codex-inline`. Parallelism is the only reason to fork; when spans are dependent, inline is simpler and loses nothing. The pre-merge QA gate runs inline by design.

The `Executor:` stamp is not decoration: a downstream judge weighs an inline verdict differently from a forked one, and an unstamped verdict is unattributable.

## The agent registry is INERT (and ships anyway)

`.codex/agents/*.toml` uses the harness's **documented** custom-agent format. At codex 0.144.1 that registry is **not read by anything** — probed at every scope and every flag. `spawn_agent` has no agent-selection parameter, so nothing can select a TOML even in principle.

It ships as forward-compatible ballast: the roster is already correct the day a codex release wires custom agents, and it self-activates then. Until that day:

- **Never design a workflow that assumes a dispatch selects one of these files.** Use the message-carried pointer above.
- Keep the TOMLs in sync with `.claude/` anyway. A registry that activates itself into staleness is worse than no registry.
- Every TOML carries this ruling in its own header, because a reader who finds one file in isolation must not conclude it dispatches today.

### gitter is deliberately NOT registered

There is no `gitter.toml` and there must not be one. Committing, merging, pushing and branch changes are gitter's alone; a Codex role gets **read-only git** (`status` / `log` / `diff` / `show`) and nothing more.

Note precisely where that boundary lives: in the working live config git is **not** gated at the execpolicy layer — it binds as LAW, stated in every role card and in the lane dialect card, not as a pin. Registering a gitter agent would advertise a capability the repo law forbids, on a registry that cannot enforce anything. `rules/repo-law.rules` ships the pin version commented out, with the trade-off written down, if you would rather have the lock than the promise.

## Settings deliberately absent from `config.toml`

An earlier version of this template shipped a Codex Teams orchestration model that **does not exist**. If you are upgrading and miss one of these, it was removed because it was untrue, not because it was trimmed:

| Removed                                                           | Why                                                                                             |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `CODEX_EXPERIMENTAL_AGENT_TEAMS = "1"`                            | Teams-gated `Agent(role, "...")` spawning is not the dispatch mechanism; `spawn_agent` is        |
| `[agents] max_threads` / `max_depth` / `job_max_runtime_seconds`   | configure a Teams scheduler that never runs the pipeline                                        |
| `[features] personality` / `codex_hooks`                          | not load-bearing; voice comes from `AGENTS.md` and the role manuals                             |
| `approval_policy = "never"`                                       | a LAUNCH decision (`-a never`), and this file is read by interactive sessions too               |
| `sandbox_mode = "danger-full-access"`                             | same — a per-launch, explicitly-authorized escalation, never a repo default                     |
| `[shell_environment_policy]`, `project_doc_max_bytes`             | not needed by the working config; add back only with a reason you can state                     |

**Launch flags belong with the launcher.** `-s workspace-write -a never` goes in the tmux command that starts a lane. Putting them here changes the human's interactive defaults out from under them.

## What NOT to do

- **Don't make Codex a requirement** — every pipeline operation must work on Claude Code alone.
- **Don't vendor protocol into `.codex/skills/`** — it is generated; run the mirror.
- **Don't hand-edit a generated pointer** — the next `generate` reverts it, silently.
- **Don't let Codex edit `.claude/`, `CLAUDE.md`, or `AGENTS.md`** — those route through the framework-change command. Claude chats have hooks fencing them; **Codex has none**, so the written ban is the only fence and it is absolute.
- **Don't put pipeline logic in a `.toml`** — past ~30 lines of `developer_instructions`, the logic belongs in the `.claude/` manual.
- **Don't use loose parenthetical lists in `developer_instructions`** — Codex can read `"(commit, lock, push)"` as authorization to perform all three.
- **Don't claim a protection you have not pinned** — a comment asserting a security property names the pin that proves it, or it does not ship.
