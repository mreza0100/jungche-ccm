# v0.51.0 — 2026-08-04

v0.50.0 made the walker engine universal but left one project-specific string inside it and put the project's config in the command manual. Both are corrected here: the engine now knows nothing about any domain, and each project's walker config lives in one file that exists for exactly that purpose.

## Added

- Mechanics: `ENGINES/wave-walker` — `securityStakesLine` joins the `args.project` profile. The security auditor's prompt used to open with one hardcoded sentence naming a specific domain's sacred data class; in a universal bundle that steered **every** linked project's deepest security pass at another product's data. It is now the project's own declaration, and its absence yields a generic, domain-free default naming only the category codes (`Sensitive data (8F), auth (8C), API surface (8D), LLM/prompt (8E) get the deepest pass.`). This was the last project-specific value in the engine. (safe-auto)
  #### → For: add `securityStakesLine` to your § Engine Config profile naming your sacred data class; omit it and the auditor keeps the same category weighting with no domain claim.
- Scripts: the bundle leak guard learns **stems and word boundaries**. It previously held one inflection of a word (`therapist`) and so read straight past its sibling (`Therapy`) — the same disease v0.47 cured on the capitalisation axis, on a new one: a denylist that knows a single inflection of a word does not know the word. Entries are now stems (`therap`, `supervis`), the sensitive-data acronyms are covered, and terms that would false-positive as substrings (`phi` inside `philosophy` — a word this engine's own source uses) match on word boundaries instead. Proven in both directions: the guard failed the build on its author's own comments mid-fix. (safe-auto)

## Changed

- Tier A: `commands/wave/walker-invariants.md` gains **§ Engine Config** as its first section — the engine's script path and the full `args.project` profile. Every project-specific walker input now lives in the one file callers already read to build `args.invariants`, so config and registry travel together. Its title and description widen accordingly: project config **and** invariant registry. (breaking)
  #### → For: move your profile out of `walker.md` into `walker-invariants.md` § Engine Config, add the engine's absolute script path there, and delete `.claude/workflows/wave-walker.js` (see Migration).
- Tier A: `commands/wave/walker.md` returns to being purely the command manual — its § Engine profile section becomes a short pointer. `walker.md` is now identical in every install; `walker-invariants.md` is what differs. Every caller site in `builder.md`, `live.md`, `orchestrator.md`, `schedule.md` reads the path and profile from § Engine Config rather than naming a repo path.
- Docs: `ENGINES/wave-walker/engine/design.md` documents the new profile field.

### Migration

- **Delete `.claude/workflows/wave-walker.js`.** Installs that symlinked it into the clone were committing a machine-absolute path into git — a link that dangles on every other checkout. Installs that copied the bundle were carrying a stale duplicate. Neither is needed: callers now name the clone's `dist/workflow.js` directly, and the Workflow harness accepts a path outside the repo (verified). Note it will not expand `~` — a tilde path resolves against the repo root, so § Engine Config carries an absolute path, written once at install.
- Adopters without a permanent clone keep using `templates/workflows/wave-walker.js` as a copied bundle; the atomic-artifact law (v0.50.0) governs both shapes — whole-file copy or rebuild, never a line-merge.
