# v0.72.0 — 2026-09-07

The chat MCP surface stops reporting work it did not do. A live sweep of every verb, verified at the OS level rather than on each tool's own success message, found eight defects — and the worst of them answered `killed <id>` for a chat whose engine was still running minutes later.

`pfm chat kill` resolved its target and then threw the resolved socket and pane away, so the kill wrote its tombstone row and never touched tmux. The row that came back said `killed` and `kind=live-claude` in the same breath, and `--exit` — the flag that would have closed the pane — failed on that path because no address was left to close. It reported success by reaching the end of a function rather than by watching a process stop, which is the one failure a verb like this must not have.

Two more verbs were dead rather than merely dishonest. `chat_reload` handed its target to a command that refuses a bare positional by design, so it failed for every input it was ever given. `chat_open` re-ran a WRITING fleet gather to find a row the caller had already resolved, and that gather wedges once the serving process has held the fleet store open for a while — so the verb hung forever inside any long-lived MCP server while the same call from a one-shot CLI returned in seconds. The remaining five are `chat_ls` telling a caller less than it knew — an inert filter, an uncapped 227 KB payload, a live chat reported as absent while it booted — and `chat_save`, whose `target` is a file path that no schema said was a file path, so passing a chat name appended a whole transcript to a file of that name.

Every fix carries a regression test that was watched failing against the unfixed code, and each was then re-verified against live processes on the rebuilt binary.

## Breaking

- Major: `pfm chat kill` — a named or id kill now ENDS the chat instead of only de-listing it. The command resolved its target and then threw the resolved socket and pane away, so `kill.Manager` wrote the tombstone row and never touched tmux: `chat_kill` answered `killed <id>` while the engine kept running, `chat_ls --killed` listed the same row as `state=idle kind=live-claude`, and `--exit` on that path failed with "--exit requires a live --self tmux pane" because there was no address left to close. Every target is now resolved first, and a live one with a socket and pane goes through the exit finisher. The message names the mechanism — `killed <id>\tclosing pane %0 on socket cc-…` versus `killed <id>\tde-listed only, no live pane closed` — because "killed" alone cannot tell a closed pane from a de-listed row, and a live chat carrying no tmux address says so on stderr rather than letting the tombstone read like a termination.
  #### → For: `pfm chat kill <name>` now closes the chat. A caller that wanted the old de-list-only behaviour has no flag for it; unkill still lifts the record.

## Fixed

- Major: `chat_reload` MCP verb — it passed its target to `pfm chat reload` as a bare positional, which that command refuses by design (a bare word there is ambiguous with the account number), so the verb failed for EVERY input with `"<target>" is not a reload argument`. It now resolves the target through the injector and reloads its tmux socket (`chat reload --sock <socket>`), and says plainly when a target resolves to no socket that only a live chat can be reloaded.
- Major: `chat_open` MCP verb — hung forever (>120s, every attempt) when served by a LONG-LIVED MCP server, while the identical call over a one-shot CLI, or over a freshly started server, returned in seconds. `openID` re-ran a WRITING fleet gather to find a row the caller had already resolved, and that gather wedges once the serving process has been holding the fleet store open for a while — which every session's own `pfm mcp chat serve` does, all day. Open now scans read-only: it needs to FIND one row, never to persist a pass.
- Minor: `chat_ls` — the documented `project` filter was inert. It was passed as the interactive picker's `InitialQuery` (its search box) and never filtered anything, so `project: ".professor"` returned every chat on the host. It is now a case-insensitive substring match against a row's project label or its full directory, and the applied filter is echoed back so an empty answer can be told from an unfiltered one.
- Minor: `chat_ls` — the killed view returned its whole history in one payload (626 rows, 227 KB) and blew the caller's tool-result budget. Rows are now capped at 200 by default (`limit`, up to 1000), with `matched` reporting how many rows the view and filter actually selected and `truncated` naming the cut outright.
- Minor: `chat_ls` — a chat that is still booting is listed with `state: "booting"` instead of being hidden. A booting row is a real chat: it owns a tmux socket and already answers `chat_inject` by name, yet `chat_ls` reported it as simply absent for its first minute after `chat_new` returned.
- Minor: `chat_ls` — a row that is killed AND live now reports `state: "killed-but-live"` instead of `idle`. That row is a contradiction, and while a kill that closes its pane makes it rare, the reader must see it as a contradiction rather than as one of its two halves: `killed: true` beside `state: idle` and `kind: live-claude` is exactly how a kill that closed nothing passed for a kill that did.
- Minor: `chat_save` — its `target` is a FILE PATH, not a chat, and its schema said nothing about that while every other verb's `target` addresses a chat. Passing a chat name created a file of that name in the server's working directory and appended the CALLING chat's whole transcript to it (142 KB, into a leak-gated repo). The field is now described as a path in the schema, the tool description leads with it, and a target carrying no directory separator is refused with the path spelling to use instead.
