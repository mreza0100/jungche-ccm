## Fixed

- Fixed: `pfm` Darwin and config diagnostics — Apple's multiline `lsof -v` revision is parsed as
  the installed version, while `config show` and `doctor` distinguish a v1 input file from the
  effective v2 schema.

- Fixed: `pfm update` — the selected release tag is stamped into both reproducible candidates,
  `--skip-harvest` reaches install and doctor, linked-worktree sources remain enumerable inside the
  isolated fence, and the target candidate—not the old running updater—performs post-build checks.

  #### → For: do not use the v0.60.0 binary's `pfm update` for this one-time repair; bootstrap the
  verified v0.60.1 binary using `INSTALL.md`, run `pfm install --yes` (add `--skip-harvest` if that
  runtime is intentionally unmanaged), then require `pfm version` and `pfm doctor` to pass. Later
  releases can use `pfm update` normally.

- Fixed: `pfm doctor` Harvester cutover — legacy standalone, foreign, malformed, and retired-auth
  Claude/Codex registrations are warnings; only exact header-free PFM loopback routes count as
  complete, and registration paths or credentials are never printed.

- Fixed: repository verification — Docker Desktop creates nested read-only fence mountpoints before
  container start, linked worktrees use a read-only mounted Git common directory, and the
  self-hosted manifest's version, three-project roster, tracked surface, and hashes are mechanically
  gated in CI.

### LLM upgrade runbook

This section is the execution contract for any LLM updating an existing installation. Read it in
full before changing the machine or a project. The machine PFM lane and each project's Professor
blueprint lane are independent: update only the lanes that are present. Never discard local
changes, overwrite customized configuration, expose credentials, or edit generated files merely
to silence a check.

#### 1. Inventory the installation and preserve local state

1. Detect the installed lanes:
   - Machine lane: `command -v pfm` succeeds.
   - Project lane: the project contains `.professor/manifest.json` and `.claude/`.
2. In every source clone and project repository involved, run `git status --short`. Classify every
   existing change. Commit or stash only through that repository's authorized Git writer; never
   reset, delete, or overwrite another session's work.
3. Record the pre-upgrade state without printing secrets:

   ```bash
   pfm version
   pfm config validate
   pfm config show
   pfm doctor
   ```

   A failure is a named pre-upgrade condition, not an empty result. Preserve its complete stderr
   and resolve or report it later.
4. If the installed machine version is older than `v0.60.0`, also read the
   [v0.60.0 migration runbook](v0.60.0.md#llm-upgrade-runbook). Perform its semantic migrations,
   but bootstrap the machine binary directly to `v0.60.1`; there is no reason to install the
   superseded `v0.60.0` binary first.

#### 2. Bootstrap the machine PFM lane to v0.60.1

Do **not** run the v0.60.0 binary's `pfm update` for this hop. Its post-build checks can execute the
old running updater instead of the candidate, so success would not prove the replacement. Install
the official checksum-verified v0.60.1 asset directly:

```bash
PFM_RELEASE_REPO=mreza0100/professor
PFM_RELEASE_TAG=v0.60.1

case "$(uname -s)" in
  Linux)  PFM_RELEASE_OS=linux ;;
  Darwin) PFM_RELEASE_OS=darwin ;;
  *) echo "unsupported operating system: $(uname -s)" >&2; exit 1 ;;
esac
case "$(uname -m)" in
  x86_64|amd64)  PFM_RELEASE_ARCH=amd64 ;;
  arm64|aarch64) PFM_RELEASE_ARCH=arm64 ;;
  *) echo "unsupported architecture: $(uname -m)" >&2; exit 1 ;;
esac

PFM_RELEASE_BINARY="pfm_${PFM_RELEASE_TAG}_${PFM_RELEASE_OS}_${PFM_RELEASE_ARCH}"
PFM_RELEASE_URL="https://github.com/${PFM_RELEASE_REPO}/releases/download/${PFM_RELEASE_TAG}"
PFM_RELEASE_TMP="$(mktemp -d)"
cd "$PFM_RELEASE_TMP"
curl -fLO "${PFM_RELEASE_URL}/${PFM_RELEASE_BINARY}"
curl -fLO "${PFM_RELEASE_URL}/SHA256SUMS"
awk -v file="$PFM_RELEASE_BINARY" '$2 == file' SHA256SUMS > "${PFM_RELEASE_BINARY}.sha256"
test -s "${PFM_RELEASE_BINARY}.sha256"
if command -v sha256sum >/dev/null 2>&1; then
  sha256sum -c "${PFM_RELEASE_BINARY}.sha256"
else
  shasum -a 256 -c "${PFM_RELEASE_BINARY}.sha256"
fi
mkdir -p "$HOME/.local/bin"
install -m 0755 "$PFM_RELEASE_BINARY" "$HOME/.local/bin/pfm"
hash -r
pfm version
```

Stop if the checksum row is missing, the checksum fails, or `pfm version` does not print
`v0.60.1`. Do not fall back to an unverified binary or a moving branch build.

Preview and apply the host reconciliation using the same Harvester choice:

```bash
pfm install
pfm install --yes
```

If the operator intentionally leaves the optional pinned Harvester runtime unmanaged, use
`pfm install --skip-harvest` for the preview and `pfm install --yes --skip-harvest` for the apply.
Do not select `--skip-harvest` merely to hide a failed provision. Read the preview in full; if the
installer names the live-service jail guard, stop the relevant service exactly as instructed and
retry rather than bypassing it.

#### 3. Validate configuration and the Harvester cutover

Run:

```bash
pfm version
pfm config validate
pfm config show
pfm doctor
pfm ls --tsv >/dev/null
```

Use `pfm doctor --skip-harvest` only when the same intentional unmanaged-runtime choice was made
above. Acceptance requires:

- `pfm version` reports exactly `v0.60.1`.
- Configuration validation succeeds. A v1 file may remain readable, but `config show` and
  `doctor` must say that the effective schema is v2 and that the input file is v1; do not rewrite
  customized account paths merely to remove that diagnostic.
- Only real Codex account homes remain under `codex.homes`; OpenCode continues to use its own
  native store. Never add a proxy or shadow Codex directory as an account.
- PFM's Chat and Harvester MCP registrations are exact loopback URLs with no bearer token or
  Authorization header. PFM MCP is local and unauthenticated by design. Preserve unrelated MCP
  servers; investigate every legacy, foreign, malformed, unreadable, or retired-auth warning by
  name instead of deleting unknown configuration.
- `pfm doctor` exits successfully, or every non-zero row is quoted and explicitly unresolved in
  the handoff. An unavailable probe is never reported as absence.

After this one-time bootstrap, later releases may use `pfm update --to vX.Y.Z` normally. The fixed
updater stamps the selected tag into both candidates, runs install and doctor through the candidate
binary, preserves linked-worktree source discovery, and propagates `--skip-harvest` consistently.

#### 4. Update each installed project blueprint lane

Run this lane once per project containing `.professor/manifest.json`:

1. Read-only preview:

   ```text
   /pcm:update check --to v0.60.1
   ```

2. Review all auto-apply, review, and manual buckets. Preserve `.professor/drift.md` KEEP-LOCAL
   entries. Cost-bearing hook, permission, environment, model, MCP, and account changes always
   require operator approval. Generated files are whole-file compiler outputs, never line merges.
3. Apply the accepted update:

   ```text
   /pcm:update --to v0.60.1
   ```

4. If the project started before v0.60.0, complete every v0.60.0 breaking migration as well:
   `/wave:sentinel` → `/wave:ccc`, `rr-fast` → `frr`, founder-name tokens → “the user”, and
   `hide` → `kill`. Keep product-domain uses of “founder”.
5. Rebuild and verify every enabled runtime layer:

   ```bash
   pfm codex build .
   pfm codex check .
   if [ -f .claude/scripts/build-opencode.mjs ]; then
     node .claude/scripts/build-opencode.mjs generate
     node .claude/scripts/build-opencode.mjs doctor
   fi
   ```

6. Run the project's real build, typecheck, full test suite, and leak/secret gate from its own
   repository law. A skipped or unavailable toolchain is a named gap, never a pass.

#### 5. Final handoff

Report separately for the machine lane and each project:

- old → new version;
- official asset name and checksum result;
- files and host surfaces changed;
- configuration, Codex-account, OpenCode, MCP, and Harvester choices;
- auto-applied, reviewed, kept-local, and manual migration counts;
- exact validation/test commands and exit results;
- every unresolved warning or unavailable gate;
- final `git status --short` for each repository.

The upgrade is complete only when the machine lane reports `v0.60.1`, `pfm config validate` and
the selected doctor mode pass, every selected project records `v0.60.1`, generated runtime checks
pass, and no pre-existing local change was discarded.
