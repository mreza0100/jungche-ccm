## Changed

- Changed: GitHub Actions runtime — Verify, Installer, and Release now use the current Node-24/ESM generations of checkout, Go setup, artifact upload, and artifact download, removing GitHub's forced deprecated-runtime compatibility path. (cost)

## Fixed

- Fixed: OpenCode indexing — reads agent, model, token, and cost data from native assistant-message JSON, so both the v1.14 store without session summary columns and newer denormalized stores index successfully.

- Fixed: transactional updates — builds release tags without detaching the live clone, advances its attached branch before installation so staged assets come from the selected release, refuses source downgrades, and restores the previous source revision before reapplying and diagnosing the old installer during rollback.

- Fixed: cross-platform update verification — preserves the installer-recorded spelling of aliased source paths across candidate and rollback installs, and waits for launched-pane process evidence to converge before declaring the live-session assertion failed.

## Migration

- Migration: `v0.61.3` → `v0.61.4` — replace the machine binary, re-run the exact installer plan after the old updater returns, and relaunch running dashboards; no adopter blueprint or configuration-schema migration is required.

  #### → For: use `pfm update --to v0.61.4`, then run `pfm install`, `pfm install --yes`, `pfm doctor`, and `pfm ls --tsv`; require the tagged Release, Installer, and Verify workflows to succeed before accepting the release.

### LLM upgrade runbook

This is the complete execution contract for an LLM upgrading Professor to v0.61.4. This corrective
release restores compatibility with the real OpenCode v1.14 database, makes source and host updates
one attached-branch transaction, and moves Professor's GitHub Actions off deprecated Node runtimes.
It does not change the adopter blueprint, configuration schema, MCP authentication, or Harvester
behavior. Preserve unrelated work and never bypass a failed gate.

#### 1. Inventory the installation

1. In the Professor source clone and every checkout sharing its Git directory, run
   `git status --short`. Stop if the update clone is dirty; do not reset, delete, or silently stash
   another session's work.
2. Record the source branch and machine state without printing credentials:

   ```bash
   git branch --show-current
   git rev-parse HEAD
   command -v pfm
   pfm version
   pfm config validate
   pfm doctor
   pfm mcp ls
   ```

3. Exit every already-running PFM dashboard after installation. A live dashboard does not reload a
   replaced executable in place.

#### 2. Install the tagged release

Installations on v0.60.1 or later use the transactional updater:

```bash
pfm update --to v0.61.4
```

The v0.61.3 updater replaces the binary correctly but can run its candidate installer before the
source branch reaches the selected tag. Therefore, after the command returns successfully, run the
v0.61.4 installer once more from the now-updated clone:

```bash
pfm install
pfm install --yes
```

Require the preview and apply plans to agree. Stop if the clone is dirty or detached, the selected
tag does not fast-forward its branch, the two candidate builds differ, installation fails, or
doctor rejects the candidate. Never force a source downgrade.

For v0.60.0 or older, or when `pfm` is absent, bootstrap the official checksum-verified asset:

```bash
PFM_RELEASE_REPO=mreza0100/professor
PFM_RELEASE_TAG=v0.61.4

case "$(uname -s)" in
  Linux)  PFM_RELEASE_OS=linux ;;
  Darwin) PFM_RELEASE_OS=darwin ;;
  *) echo "unsupported operating system: $(uname -s)" >&2; exit 1 ;;
esac
case "$(uname -m)" in
  x86_64|amd64)  PFM_RELEASE_ARCH=amd64 ;;
  arm64|aarch64) PFM_RELEASE_ARCH=arm64 ;;
  *) echo "unsupported architecture: $(uname -m)" >&2; exit 1 ;;
esac

PFM_RELEASE_BINARY="pfm_${PFM_RELEASE_TAG}_${PFM_RELEASE_OS}_${PFM_RELEASE_ARCH}"
PFM_RELEASE_URL="https://github.com/${PFM_RELEASE_REPO}/releases/download/${PFM_RELEASE_TAG}"
PFM_RELEASE_TMP="$(mktemp -d)"
cd "$PFM_RELEASE_TMP"
curl -fLO "${PFM_RELEASE_URL}/${PFM_RELEASE_BINARY}"
curl -fLO "${PFM_RELEASE_URL}/SHA256SUMS"
awk -v file="$PFM_RELEASE_BINARY" '$2 == file' SHA256SUMS > "${PFM_RELEASE_BINARY}.sha256"
test -s "${PFM_RELEASE_BINARY}.sha256"
if command -v sha256sum >/dev/null 2>&1; then
  sha256sum -c "${PFM_RELEASE_BINARY}.sha256"
else
  shasum -a 256 -c "${PFM_RELEASE_BINARY}.sha256"
fi
mkdir -p "$HOME/.local/bin"
install -m 0755 "$PFM_RELEASE_BINARY" "$HOME/.local/bin/pfm"
hash -r
test "$(pfm version)" = "pfm v0.61.4"
```

Never install an asset with a missing or mismatched checksum.

#### 3. Reconcile and verify the host

From the Professor source clone, run:

```bash
test "$(git branch --show-current)" != ""
git merge-base --is-ancestor v0.61.4 HEAD
pfm install
pfm install --yes
test "$(pfm version)" = "pfm v0.61.4"
pfm config validate
pfm doctor
pfm mcp ls
pfm ls --tsv >/dev/null
```

Stop on a foreign-file conflict or any difference between preview and apply. Acceptance requires an
attached source branch containing v0.61.4, a clean doctor, readable enabled engines, loopback-only
unauthenticated Professor MCP routes, and successful fleet enumeration.

#### 4. Prove OpenCode compatibility and update rollback

1. On a host with an OpenCode database, run `pfm ls --tsv` and require OpenCode sessions to enumerate
   without any `no such column` error. A v1.14 database does not contain aggregate agent, model,
   token, or cost columns on `session`; v0.61.4 derives those values from native assistant-message
   JSON. Do not add columns or rewrite the user's database to satisfy PFM.
2. Confirm the source branch remains attached after the update. A detached checkout is failure.
3. If a disposable update failure is intentionally injected, require the old binary and previous
   source revision to be restored before the previous installer and doctor run. Any reported
   rollback residue is failure and requires manual repair; do not repeat the update blindly.

#### 5. Require tagged CI and close the update

Verify the GitHub release is public and non-draft, contains four platform binaries plus
`SHA256SUMS`, and that every asset digest matches its checksum row. Require the Release, Installer
end-to-end verification, and Verify workflows triggered by the v0.61.4 release commit to finish
green. The Darwin installer job must converge when its temporary source path has an aliased spelling,
and the Verify job must observe the launched fixture as live without a one-shot scheduling race.

Record the installed version, source branch and revision, doctor output, installer summary, CI URLs,
asset checksums, and final Git status. Do not mutate the published tag, bypass checksums, or claim a
network-dependent proof that did not run.
