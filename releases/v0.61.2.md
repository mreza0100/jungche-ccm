### LLM upgrade runbook

This is the complete execution contract for an LLM upgrading an existing Professor installation to
v0.61.2. Read it before changing the machine. Preserve unrelated work, never expose account or MCP
credentials, and name an unavailable check as a gap rather than a pass. This release changes the
machine PFM lane only; it contains no adopter-blueprint template migration.

#### 1. Inventory and protect the current installation

1. In the Professor source clone and every checkout sharing its Git directory, run
   `git status --short`. Do not reset, delete, overwrite, or silently stash another session's work.
   Stop if the update clone is dirty; route required commits through that repository's authorized
   Git writer.
2. Record machine state without printing credential files:

   ```bash
   command -v pfm
   pfm version
   pfm config validate
   pfm config show
   pfm doctor
   pfm mcp ls
   ```

3. Record whether a PFM dashboard is already running. A running process does not hot-reload a
   replaced executable and must be exited and relaunched after installation.
4. If the installed version is v0.60.0 or older, also read the
   [v0.60.1 one-time updater repair](v0.60.1.md#llm-upgrade-runbook). Do not ask that older updater
   to validate its own replacement.

#### 2. Upgrade the machine PFM lane

For v0.60.1 or later, use the tagged transactional updater:

```bash
pfm update --to v0.61.2
```

Read the candidate-build, reproducibility, install, doctor, and rollback receipts. Stop if the
source clone is dirty, the selected tag is not v0.61.2, the two candidate binaries differ, install
fails, or doctor rejects the candidate. Never replace a failed tagged transaction with a build from
a moving branch.

For v0.60.0 or older, or when `pfm` is absent, bootstrap the official asset directly:

```bash
PFM_RELEASE_REPO=mreza0100/professor
PFM_RELEASE_TAG=v0.61.2

case "$(uname -s)" in
  Linux)  PFM_RELEASE_OS=linux ;;
  Darwin) PFM_RELEASE_OS=darwin ;;
  *) echo "unsupported operating system: $(uname -s)" >&2; exit 1 ;;
esac
case "$(uname -m)" in
  x86_64|amd64)  PFM_RELEASE_ARCH=amd64 ;;
  arm64|aarch64) PFM_RELEASE_ARCH=arm64 ;;
  *) echo "unsupported architecture: $(uname -m)" >&2; exit 1 ;;
esac

PFM_RELEASE_BINARY="pfm_${PFM_RELEASE_TAG}_${PFM_RELEASE_OS}_${PFM_RELEASE_ARCH}"
PFM_RELEASE_URL="https://github.com/${PFM_RELEASE_REPO}/releases/download/${PFM_RELEASE_TAG}"
PFM_RELEASE_TMP="$(mktemp -d)"
cd "$PFM_RELEASE_TMP"
curl -fLO "${PFM_RELEASE_URL}/${PFM_RELEASE_BINARY}"
curl -fLO "${PFM_RELEASE_URL}/SHA256SUMS"
awk -v file="$PFM_RELEASE_BINARY" '$2 == file' SHA256SUMS > "${PFM_RELEASE_BINARY}.sha256"
test -s "${PFM_RELEASE_BINARY}.sha256"
if command -v sha256sum >/dev/null 2>&1; then
  sha256sum -c "${PFM_RELEASE_BINARY}.sha256"
else
  shasum -a 256 -c "${PFM_RELEASE_BINARY}.sha256"
fi
mkdir -p "$HOME/.local/bin"
install -m 0755 "$PFM_RELEASE_BINARY" "$HOME/.local/bin/pfm"
hash -r
test "$(pfm version)" = "pfm v0.61.2"
```

Stop if the checksum row is absent, checksum verification fails, or the version is not exact. Never
substitute an unverified binary.

#### 3. Preview and apply host reconciliation

Use the same Harvester choice for preview and apply:

```bash
pfm install
pfm install --yes
```

The preview must enumerate concrete writes, links, deletions, and conflicts before apply mutates the
host. Stop on a foreign-file conflict; do not delete it merely to make install pass. Use
`--skip-harvest` on both commands only when the operator explicitly chooses to leave the pinned
Harvester runtime unmanaged. Professor MCP routes remain loopback-only and unauthenticated; do not
add tokens or authorization headers.

Exit every pre-upgrade PFM dashboard and launch a fresh `pfm ls` before testing the new behavior.

#### 4. Prove the installed machine

Run the base gate:

```bash
test "$(pfm version)" = "pfm v0.61.2"
pfm config validate
pfm config show
pfm doctor
pfm ls --tsv >/dev/null
```

Acceptance requires the exact version, schema-2 configuration, a healthy doctor, and successful
fleet enumeration across every configured engine. A missing or unreadable store is a named failure,
not an empty success.

Prove complete Google Drive processing with a disposable public PDF whose final page is known:

```bash
DRIVE_FILE_URL='https://drive.google.com/file/d/FILE_ID/view'
pfm harvest --refresh --size-only --json "$DRIVE_FILE_URL" > drive-receipt.json
jq -e '.kind == "pdf" and .method == "google-drive-download" and .chars > 0' drive-receipt.json
pfm harvest ask --engine codex -p \
  'State the page count and cite one fact found only on the final two pages.' \
  "$DRIVE_FILE_URL"
```

Use a real public file-share URL, not a Drive folder or browser-preview URL copied from page HTML.
Require the receipt to name `pdf` and `google-drive-download`, and compare the answer with the known
final pages. A preview-only answer, missing final-page evidence, or fallback to Jina is failure.

Prove deactivation only with a disposable live chat:

1. Start a disposable chat with `pfm chat new --name PFM_DEACTIVE_PROBE --engine codex` (or another
   configured engine).
2. Open `pfm ls`, select that row, move to **Deactive**, and press Enter.
3. Require the dashboard to remain open, the row to disappear immediately, and every unrelated chat
   to remain live. Exit the dashboard normally afterward.
4. Reopen `pfm ls`; the disposable chat may be resumable, but its old pane/process must be gone.

Never use a real working chat for this proof.

#### 5. Understand and verify update discovery

Each valid `pfm ls` invocation starts one detached HEAD lookup of Professor's latest GitHub release.
It does not wait, print into the picker, or consume its own result. A successful result is cached for
the next invocation; concurrent invocations share a lock, and a failed lookup preserves the last
successful notice.

At v0.61.2 while v0.61.2 is latest, no update banner is expected. When a newer release exists:

1. Run `pfm ls` once and exit normally; this invocation performs the silent lookup.
2. Open `pfm ls` again. Before the merged new-chat row, require a full-width blinking gold
   **PROFESSOR UPDATE** banner with Claude, Codex, and OpenCode choices available for the configured
   roster.
3. Choose an engine and press Enter. Require it to open in the recorded Professor source clone and
   first present the release overview and migration impact.
4. The engine must ask for explicit approval before running `pfm update`. Declining approval must
   leave the source clone, binary, and host wiring untouched.

The banner is an action, not a chat: Hide and Deactive must not apply to it.

#### 6. Adopter projects and final acceptance

v0.61.2 contains no `blueprint/` template changes. Do not run `/pcm update` or rewrite adopter
manifests solely for this machine-only patch. Existing project customizations and runtime mirrors
remain untouched.

Record the final version, doctor output, installer summary, Drive receipt, disposable deactivation
result, and Git status. Success means the official v0.61.2 binary is installed, enabled engines are
readable, the complete Drive file reaches Harvester, Deactive leaves PFM open, and update discovery
remains silent until a later invocation has a real newer release to show.

If any transaction fails, preserve its rollback receipt and confirm the previous binary remains
operational. Do not bypass checksums, force-reset local work, mutate a published tag, or claim a
network-dependent proof that did not run.
